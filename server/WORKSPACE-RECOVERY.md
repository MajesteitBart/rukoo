# Workspace recovery proposal

These procedures recover **one team's workspace**. Account and Book remain live authorities with their existing recovery procedures. The backup contains no personal records, credential verifiers, recovery factors or device sessions. A workspace import cannot change a personal password, release a booking handle or manufacture an account incarnation.

| Profile | What the operator can recover |
| --- | --- |
| Basic (first release) | Committed live storage survives normal restart. The supported CLI refuses historical rewind/import. On Cloudflare a rollback is a deploy that calls the storage API, outside that CLI, and the first thing an operator reaches for after a bad migration. It undoes every removal, ban and redaction since that point, so the runbook treats it as an import: the workspace starts fenced under a new restore generation, and its owner gets an export followed by a new workspace. On declared loss or unexplained regression, create a new empty workspace. Server-local state alone cannot detect a consistent full-volume rewind. A returning device may have a checkpoint that proves it. |
| Protected (follow-on) | Requires a surviving or independently recovered Account authority with verified identity continuity. Provides workspace checkpoint and file copies plus replay of acknowledged restrictions. If accounts were also lost and cannot be verified, only a new empty workspace can reopen. New content after the last checkpoint can be lost. A pending restriction may need to be reapplied after primary loss. Show the actual checkpoint, journal watermark and pending-action policy. |

Both profiles offer authorized export for reading. An export cannot reconstitute grants. Enable protected mode only after its first independently verified complete checkpoint. Live personal account and booking operations never depend on this choice. The host advertises the active profile and effective retention; a backup outage cannot silently downgrade protection.

## One atomic checkpoint cut

Workspace owns the directory, every conversation log and its authoritative tables in **one** SQLite database or equivalent transactional VPS database. The application uses logical deltas; it requires no native copy-on-write snapshot, ongoing cross-request SQL read transaction, or fan-out to thousands of idle DMs.

1. **Capture.** In protected mode every authoritative mutation appends its logical after-images/tombstones under a monotonic workspace backup revision in the **same transaction**. Include read/dedupe state, grants, membership, job/attempt lifecycles and storage references. Classify each mutation (restrict/remove, neutral, grant). A central writer or database triggers must enforce coverage and fail on an unclassified mutation type. Rebuild derived indexes from source. On enabling protection for existing data, first start delta capture, scan by stable primary key and replay all captured revisions over the seed through a later cutoff. Verify counts/digests before certifying the base.
2. **Cut.** The independently stored restriction chain has a single active writer per protected workspace and a contiguous tip. In the local database track `appliedJournalPrefix`: the highest *contiguous* external revision with matching hash whose complete effects are already applied locally. It is safe for that prefix to lag the external tip. A single local transaction captures checkpoint E, workspace lineage and generation, data revision Dcut, and this prefix Jcut/hash. Pin the required source segments, file references and retention metadata at that cut. Publication never samples Jcut again. A completed removal between the cut and publication has either been captured durably in Dcut or has a later journal revision to replay.
3. **Stage and publish.** An asynchronous exporter with live-source read access, a separately scoped backup write credential and the operator's public encryption key seals deltas/files to the recovery public key, uploads immutable segments, and reads only the metadata/receipts needed to verify storage. It does not have the historical decryption key. Create independently encrypted copies of all referenced file bytes, including files later collected from primary storage; keep them pinned until the last referencing backup expires. An isolated operator-controlled compactor with the offline recovery role decrypts verified segments to build a new sealed base when necessary. It can alternatively reseed from current live data for future backups. Never overwrite or unpin an older backup dependency before its retention expires. Publish a signed manifest with the original Dcut, Jcut, hashes and complete independent object inventory. Incomplete exports never replace the last verified manifest. Daily checkpoints and 30-day backup retention are initial defaults.
4. **Bound work.** Taking the cut appends a constant-size control record; a revision/retention barrier protects all older dependencies without copying them or iterating rooms inside that transaction. Stream/verify the graph outside the transaction. Qualify cut latency and segment/verification cost with full message history and the published conversation cap. Enforce a separately allocated local spool quota with soft and hard watermarks. At the soft mark alert and prioritize export. At the hard mark refuse new content/uploads before commitment with a retry interval. Reserve capacity for restrictive intents and control work; if even that reserve fails, fence affected access rather than falsely reporting completion. No spillover into Account or Book. Show last complete checkpoint and lag.

## Restrictions and writer generations

The local Workspace is the authority for live actions. Apply a ban, role reduction, DM close, sponsor revocation, redaction, attachment removal, retention policy change or workspace deletion with its restriction outbox entry in one transaction. Retention expiry itself stays out of the journal: a restore applies the policy again by time. Pending means “applied here, backup confirmation pending.” **Complete** means the independent append and tip update succeeded. Once the deletion of an account retires its incarnation, all workspace admissions requiring it fail immediately. Workspace receives an independently retryable cleanup notification; Account need never wait for the external journal.

A grant has an immutable logical admission ID minted at actual admission. Restore preserves that ID. The effective authorization is the pair (restore generation, logical admission ID); a changed generation invalidates previously issued authorizations and queued work. Restrictive journal entries target the logical admission ID, actor and room, independent of the effective restore generation.

A real leave/rejoin creates a new logical admission ID. Thus a removal during generation 2 still removes that original logical admission when replaying a generation-1 checkpoint. If a target never existed at that checkpoint, retain its logical-ID tombstone for replay and never apply it to an unrelated admission. An entry carries stable operation ID, workspace/resource incarnation, affected IDs or ranges, security effect and generation. A post redaction covers its attachment links in backups as well as the live source. Use one serializer per workspace, not a host-wide journal. Write an immutable entry and conditionally advance the independent tip from the prior hash and writer fence. Return completion only after that CAS succeeded. If the reply is lost, reconcile the same operation from the verified tip and record its contiguous applied prefix locally. Unlinked entries are never treated as confirmed.

The independently administered destination must pass conditional updates, immutable retention, history verification and read-after-write tests. Protect the tip against rollback independently of the primary and give only the offline restore role the decryption and sealing/cutover authority. A compromised live operator can alter live workspace content as disclosed; the design addresses operational recovery.

A checkpoint needs only restrictive changes after Jcut; replay can overlap already applied entries idempotently. For an ownership transfer apply the old owner's loss. Restore a successor only from a verified, committed transfer record for both current incarnations. When only the reduction can be proved, activate succession mode: ordinary chat may resume, owner-only actions remain disabled pending audited appointment. A new identity sharing a deleted owner's email cannot claim the old DMs.

## Cold start and historical restore

Ordinary eviction, hibernation and app restart read local consistency signals only: check the workspace generation, durable revision/head anchors and local receipts. Missing referenced live state or a regression against a locally confirmed cut fences the affected scope. A consistent single-volume rewind cannot be detected from that same volume. A returning device can supply its authenticated checkpoint as independent evidence of a regression, as specified by the sync contract. The keys that verify checkpoints live in the host secret store, outside the Workspace database, and a device pins their ID: a checkpoint ahead of the server that can no longer be verified quarantines the workspace on that device instead of resetting it. Devices that have seen neither side of the divergence provide no witness. In protected mode, operator deployment checks and periodic verification compare independently known cuts and restriction tips. A routine destination outage raises an alert, stops *verified* new checkpoints and leaves healthy chat available with the stated pending semantics. A detected regression, declared storage rollback or import fences the workspace and requires independent verification. The basic CLI rejects historical import, because it has no evidence for safe replay.

1. Quarantine the target and stop old ingress, automatic jobs, grants and notifications. Load a signed, fully verified checkpoint in isolation. Verify independent file copies without using the primary bucket. Check every mandatory segment, lineage, generation and checkpoint hash.
2. **Seal the old writer at the external store.** Recovery uses a privileged CAS loop on the previous writer generation and current tip. Every previous-generation completion competes on this same state. An append that won first belongs in the final tip Jend; a losing append can no longer be acknowledged. The seal names that exact immutable tip. Fence remaining old routes/instances before opening new traffic. Resume an interrupted restore from the same seal. Never reactivate a sealed writer.
3. Verify and replay the entire chain **after the Jcut captured at the local cut, through Jend inclusive**. Never use a later watermark from manifest publication. Apply the effective retention policy through the proposed reopening time, including any expiry that fell during the outage. Rebuild live projections, entitlements and quotas only after these expirations, erasures and removals. Downloads and history enforce the current time cutoff again at serving time. A broken or unavailable chain leaves the affected scope sealed; an unknown affected scope keeps the whole workspace offline. Revoke old workspace tickets, invitations, runner leases and credentials; preserve each restored grant's stable logical admission ID under a new unpredictable restore generation. Use a new writer generation anchored to the seal. Publish each seal and successor relationship into the same independently retained append-only chain. From an older checkpoint, traverse every intervening writer generation in order; tip verification must cover all branches eligible to serve traffic and reject a fork.
4. After erasure replay, the offline restore role decrypts surviving, independently retained files into a new private primary bucket/prefix, verifying size and SHA-256. Map stable attachment IDs to the replacement immutable object keys inside the isolated import. Exclude tombstoned files from the live namespace. The serving service gets ordinary scoped storage credentials only, never backup decryption authority. Fail the affected scope closed on a required file whose bytes cannot be verified. Check continuing human grants against the current trusted Account authority. If the identity service was also lost or rewound, old verifiers, cached sessions, email addresses or restored account IDs cannot establish continuity for workspace history. Recover identity separately. Until authoritative continuity is independently established keep the old private archive sealed and offer a *new empty workspace* for new participants. Workspace recovery never freezes a personal credential or changes Book's device binding.
5. Devices replace their authorized views and delivery cursors and reconcile uncertain attempted sends without automatic replay. For still-authorized rooms, compare stable IDs and show a count of locally received messages missing from the new server state before purging. Never display counts or text for an inaccessible scope. Runners re-enroll with a new trigger cutoff. Existing signed file URLs have the documented short lifetime; disable old access paths or wait for expiry before reusing a bucket namespace. Resume workspace traffic only after these checks.

## Acceptance drill

- Back up at conversation head 100, let a phone reach 120, and **after the cut but before publishing its manifest** remove a guest and redact a PDF. Obtain completed receipts. Destroy the test workspace's primary database and file bucket, seal the old writer and restore. The guest gets access denied, the post's file is unavailable and the phone displays the new generation's 101. Upload a separate surviving control file before the cut and verify an authorized member downloads it through the normal API from the replacement bucket with a matching digest. Include a file aged 89 days at the cut under a 90-day policy and restore three days later. Neither the post nor its file may be served. The younger control must still download. A still-authorized phone gets a count of missing received IDs, and a removed device gets no private details.
- Delay an old writer's tip update across cutover. It must either appear in Jend and be replayed, or lose the CAS and never report completion. Repeat with journal outage: live restrictions apply, status remains pending, and only independently recorded restrictions survive full loss. After a broken-chain restore the service stays sealed. Test ownership transfer, lost successor, and uncertain identity lineage.
- Run a protected checkpoint under the published load and at the conversation limit with seeded 30-day dedupe history. Validate complete mutation classification, cut latency, spool bounds, encryption, compaction and retained files with an actual qualified recovery destination. Confirm normal password recovery and Book writes during both a checkpoint and a workspace restore.
- Restore E with grant L, reopen generation 2, and complete removal of L. Lose the primary again before the next checkpoint. Restore E again, replay through both writer seals and the completed removal, and verify generation 3 cannot read L's messages or get a file URL. A new, explicitly authorized admission uses a different L.
